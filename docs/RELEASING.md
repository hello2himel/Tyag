# Releasing Tyag

Tyag ships the **same** React/Vite bundle on every platform. A release is a
single git tag that produces web, Android, iOS, Windows (NSIS + MSI), macOS
(DMG), Linux AppImage/deb/rpm and Linux Flatpak (Tauri 2 + system WebView)
artifacts plus checksums, and a draft GitHub release that a maintainer reviews
and publishes.

Everything here is designed so that **no signing key, password or certificate
is ever committed**. Builds are produced by CI from the tag
(`.github/workflows/release.yml`) or locally with the commands in
[BUILDING.md](BUILDING.md).

---

## 1. Versioning

* **Semantic versioning** `MAJOR.MINOR.PATCH`, single source of truth:
  the `version` field in the root `package.json`.
* Tags are `vX.Y.Z` (e.g. `v1.0.0`); `release.yml` fails if the tag does not
  match `package.json`.
* Product releases follow user-facing meaning: `MINOR` for new features,
  `PATCH` for fixes, `MAJOR` only for breaking data/backup compatibility.

### Version bump checklist

Bump these **together** in one commit before tagging:

| File | Field | Notes |
| --- | --- | --- |
| `package.json` | `version` | source of truth, e.g. `1.1.0` |
| `apps/mobile/android/app/build.gradle` | `versionCode` + `versionName` | `versionCode` is an integer that must strictly increase for Play Store; `versionName` = semver |
| `apps/mobile/ios/App/App.xcodeproj/project.pbxproj` | `MARKETING_VERSION` + `CURRENT_PROJECT_VERSION` | in both Debug and Release configurations |
| `flatpak/org.tyag.Tyag.metainfo.xml` | `<release version= date=>` | newest release first; AppStream requires it |
| `apps/desktop/package.json` | `version` | keep in step with the root version |
| `apps/desktop/src-tauri/tauri.conf.json` | `version` | Tauri bundle version (must equal the root version; `tauri build` refuses on mismatch) |
| `apps/desktop/src-tauri/Cargo.toml` | `version` | Rust crate version; `Cargo.lock` is refreshed by the build (commit it) |
| `apps/mobile/package.json`, `packages/core/package.json` | `version` | keep in step with the root version |

Then:

```bash
pnpm install --frozen-lockfile   # lockfile must be unchanged; commit it if deps changed
pnpm typecheck && pnpm test && pnpm --filter @tyag/web build && pnpm audit:privacy
```

Finally update the changelog/release notes draft and commit everything before
tagging (CI builds from the tag).

## 2. Artifact names

All artifacts are attached to the GitHub release and covered by
`SHA256SUMS.txt` (generated by the publish job and per-platform CI).

| Platform | Artifact | Built by |
| --- | --- | --- |
| Web/PWA | `Tyag-<version>-web.zip` | `web` job (`apps/web/dist`) |
| Android | `Tyag-<version>-debug.apk` (CI fallback) / `Tyag-<version>-release.apk` / `Tyag-<version>-release.aab` | `android` job |
| Linux AppImage | `Tyag-<version>-<arch>.AppImage` | `linux` job (Tauri) |
| Linux deb | `Tyag-<version>-<arch>.deb` (`arch` = `amd64`) | `linux` job (Tauri) |
| Linux rpm | `Tyag-<version>-<arch>.rpm` (`arch` = `x86_64`) | `linux` job (Tauri) |
| Linux Flatpak | `Tyag-<version>-<arch>.flatpak` | `flatpak` job (Tauri on `org.gnome.Platform//48`) |
| Windows | `Tyag-Setup-<version>-<arch>.exe` (NSIS) | `windows` job (Tauri) |
| Windows MSI | `Tyag-<version>-<arch>.msi` | `windows` job (Tauri) |
| macOS | `Tyag-<version>-<arch>.dmg` | `macos` job (Tauri, unsigned) |
| iOS (unsigned) | `Tyag-<version>-unsigned.xcarchive.zip` | `ios` job |
| Checksums | `SHA256SUMS.txt` | publish job (all files) |

`<arch>` is `x86_64`/`aarch64` for Linux, `x64`/`arm64` for Windows/macOS,
matching the Tauri bundle arch (`uname -m` on Linux, `process.arch` in `scripts/collect-tauri-artifacts.mjs`). The Tauri builds write native names first (`Tyag_1.0.0_amd64.AppImage`, `Tyag_1.0.0_x64-setup.exe`, …); the collection script renames them to the stable scheme above and generates `SHA256SUMS.txt`.

## 3. Signing and secrets (never in the repo)

### Android (APK/AAB)

The release keystore is generated once, stored in a password manager, and
provided to CI as secrets:

| Secret | Value |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | `base64 -w0 "$HOME/tyag-release.jks"` |
| `ANDROID_KEYSTORE_PASSWORD` | store password |
| `ANDROID_KEY_ALIAS` | key alias (e.g. `tyag`) |
| `ANDROID_KEY_PASSWORD` | key password |

The workflow writes them to `$RUNNER_TEMP/tyag-release.jks`, exports the
`TYAG_*` variables, builds, and deletes the keystore afterwards. Locally the
same variables are read by `apps/mobile/android/app/build.gradle`; without them
the release variant falls back to **debug signing** (useful for testing, not
for distribution).

Keystore creation (one-time, outside the repo):

```bash
keytool -genkeypair -v -keystore "$HOME/tyag-release.jks" -alias tyag \
  -keyalg RSA -keysize 4096 -validity 10000 -storetype PKCS12
```

Play Console upload uses the `.aab`; `versionCode` must increase monotonically.
Never delete or rotate the upload keystore without using Play App Signing key
rotation, losing it means losing update rights.

### Windows (NSIS installer + MSI)

Tauri builds unsigned by default; CI needs no secrets. For signed releases,
configure Tauri's Windows signing options (certificate thumbprint or `.pfx`
path plus timestamp URL, see the Tauri bundler docs) and provide the
certificate material/password as CI secrets only; never commit it. Signing can
also be done as a post-processing step with `signtool` before uploading.

Unsigned installers are fine for testing; SmartScreen will warn end users.

### macOS (DMG)

Unsigned DMGs work locally but Gatekeeper blocks them on other Macs. CI builds
them **unsigned** on purpose: `apps/desktop/src-tauri/tauri.conf.json` sets
`bundle.macOS.signingIdentity: null`, so no certificate discovery happens and no
signing secrets are required. For a distributable DMG, a maintainer signs and
notarizes it on macOS with their Developer ID identity
(`APPLE_SIGNING_IDENTITY` + `APPLE_ID`/`APPLE_PASSWORD`/`APPLE_TEAM_ID` for
notarization, passed only through the environment). No certificate, password or
key is ever committed. Tauri builds both the Intel (`x64`) and Apple Silicon
(`aarch64`) DMGs natively on the matching macOS runner.

### iOS

Store builds require an Apple Developer account. The CI workflow produces an
**unsigned** `.xcarchive`; a maintainer (or a signing job with
`DEVELOPMENT_TEAM`, a distribution certificate and a provisioning profile)
signs and exports it, then uploads to App Store Connect with Transporter/Xcode.

### Flatpak / Flathub

The `.flatpak` bundle is unsigned: users install it with
`flatpak install --user --bundle …` (or a maintainer submits the manifest to
Flathub). No Flathub token is required for the GitHub release artifact. If you
mirror a Flatpak repository, use a GPG key stored only in CI secrets.

## 4. Release procedure

1. **Freeze and verify** `main`:
   ```bash
   pnpm install --frozen-lockfile
   pnpm typecheck && pnpm test
   pnpm --filter @tyag/web build && pnpm audit:privacy
   ```
2. **Bump versions** (table above) and commit:
   `chore(release): vX.Y.Z`.
3. **Tag and push**:
   ```bash
   git tag -a vX.Y.Z -m "Tyag vX.Y.Z"
   git push origin main --tags
   ```
4. **Watch the `Release` workflow** (Actions → Release). It runs eight build
   jobs in parallel (web, android, linux AppImage, flatpak, windows, macos,
   ios), flattens all artifacts, writes `SHA256SUMS.txt` and creates a **draft**
   GitHub release named `Tyag vX.Y.Z` with generated notes.
5. **Verify the draft**:
   * every expected artifact from §2 is attached (a missing `ios`/`macos`
     artifact means a runner failure, inspect logs before publishing);
   * `SHA256SUMS.txt` is attached and matches the files;
   * release notes look right (edit them in the GitHub UI).
6. **Publish** the draft when the artifacts are verified.
7. **Store uploads** (manual, per store):
   * Google Play Console ← `…-release.aab` (internal → alpha → production);
   * App Store Connect ← signed iOS archive;
   * Microsoft Store / direct download ← signed `.exe`;
   * macOS: notarized `.dmg` (direct download);
   * Flathub: submit/update `flatpak/org.tyag.Tyag.yml` on Flathub;
   * web: Netlify builds `main` automatically (`netlify.toml`), or upload
     `Tyag-<version>-web.zip` to any static host.

### Local release build (no CI)

```bash
pnpm install --frozen-lockfile
pnpm --filter @tyag/web build
pnpm build:desktop                     # Tauri release binary (no installer bundles)
pnpm --filter @tyag/desktop dist:linux   # AppImage + deb + rpm (+ SHA256SUMS.txt)
pnpm build:android                     # debug unless TYAG_* signing vars set
pnpm build:flatpak                     # needs flatpak-builder/docker
```

Artifacts land in `apps/desktop/release/`, `apps/mobile/dist/`,
`flatpak/dist/`. Compute checksums with `sha256sum` (Linux) or `shasum -a 256`
(macOS) before uploading.

## 5. Verifying a release (for users and maintainers)

```bash
# download the artifact + SHA256SUMS.txt from the GitHub release, then:
sha256sum -c SHA256SUMS.txt          # Linux
shasum -a 256 -c SHA256SUMS.txt      # macOS
```

Platform checks:

* **Web**: host the zip contents statically; the app must work with the network
  disabled after first load (service worker).
* **Android**: `apksigner verify --print-certs <apk>` (CI does this), then
  `adb install -r` on a device.
* **AppImage**: `chmod +x Tyag-*.AppImage && ./Tyag-*.AppImage` (needs the
  system WebKitGTK 4.1 and `libfuse2`; `--appimage-extract-and-run` works
  without FUSE).
* **deb/rpm**: `sudo apt install ./Tyag-*.deb` or `sudo dnf install
  ./Tyag-*.rpm`; then launch `Tyag` from the application menu.
* **Windows MSI**: `msiexec /i Tyag-*.msi`; NSIS installer is unsigned
  (SmartScreen warning expected).
* **macOS DMG**: unsigned, right-click → Open the first time on other Macs.
* **Flatpak**: `flatpak install --user --bundle Tyag-*.flatpak` then
  `flatpak run org.tyag.Tyag`; `flatpak info --user --show-permissions
  org.tyag.Tyag` must show no network and no home access; the database
  lives under `~/.var/app/org.tyag.Tyag/data/app.tyag.Tyag/`.
* **Tauri desktop**: first launch creates `tyag.db` in the Tauri app-data
  directory (`~/.local/share/app.tyag.Tyag` on Linux,
  `~/Library/Application Support/app.tyag.Tyag` on macOS,
  `%APPDATA%\app.tyag.Tyag` on Windows); the window must render the
  embedded bundle from `tauri://localhost` (Linux/macOS) or
  `http://tauri.localhost` (Windows) and never make a network request.

## 6. CI/CD reference

| Workflow | Release responsibility |
| --- | --- |
| `.github/workflows/release.yml` | tag `v*` → all platform artifacts + `SHA256SUMS.txt` + draft GitHub release |
| `.github/workflows/ci.yml` | PR/main gate: typecheck, tests, web build, privacy audit, Tauri release binary + WebKitGTK linkage + Rust command tests |
| `.github/workflows/android.yml` | per-push APK (debug) / tag APK+AAB (signed when secrets exist) |
| `.github/workflows/flatpak.yml` | `.flatpak` bundle |
| `.github/workflows/desktop-{linux,windows,macos}.yml` | Tauri: AppImage+deb+rpm / NSIS+MSI / DMG |
| `.github/workflows/ios.yml` | unsigned simulator build + unsigned `.xcarchive` |

Actions caches: pnpm store (`setup-node cache: pnpm`), Rust `target/`
(`Swatinem/rust-cache`), Tauri bundler tools (`~/.cache/tauri`,
`~/AppData/Local/tauri`, linuxdeploy/AppImage runtime, NSIS/WiX), Gradle
(`gradle/actions/setup-gradle`).

Tauri notes for release engineers:
* the Linux jobs install the WebKitGTK 4.1 development packages before building;
* `rpm` packages need `rpmbuild` (installed in the Linux CI job; not present on
  every developer machine, `dist:linux` will then fail at the rpm step, so use
  the CI artifact or install `rpm`);
* no signing secrets are referenced by any desktop job; all desktop artifacts
  are unsigned unless a maintainer signs them explicitly.

## 7. Rollback / yanking

* **GitHub release**: unpublish or mark the draft/unpublished release; delete
  the tag only if the build was never consumed (`git tag -d vX.Y.Z` +
  `git push origin :refs/tags/vX.Y.Z`) and ship `vX.Y.(Z+1)` instead.
* **Play Store**: roll out a new `versionCode`; you cannot decrease it. Use
  staged rollout halt + hotfix.
* **App Store**: remove from sale or expedite a new build; builds are immutable.
* **Web**: redeploy the previous `Tyag-<version>-web.zip` (service workers
  update on next load; keep the previous release zip).
* **Flatpak/AppImage/desktop**: publish patched artifacts with the next patch
  version; never replace an already-published file with different bytes.
* Keep `SHA256SUMS.txt` attached to old releases so users can verify what they
  downloaded.


## Published releases

Publishing is idempotent: re-running this workflow uploads rebuilt artifacts to an existing *draft* release, and leaves an already-published release's assets untouched (the rebuilt files remain available as workflow artifacts). A maintainer can therefore publish locally built, signed artifacts first (as done for `v1.0.0`) and still validate the pipeline.
