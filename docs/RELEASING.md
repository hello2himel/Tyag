# Releasing deUrge

deUrge ships the **same** React/Vite bundle on every platform. A release is a
single git tag that produces web, Android, iOS, Windows, macOS, Linux AppImage
and Linux Flatpak artifacts plus checksums, and a draft GitHub release that a
maintainer reviews and publishes.

Everything here is designed so that **no signing key, password or certificate
is ever committed**. Builds are produced by CI from the tag
(`.github/workflows/release.yml`) or locally with the commands in
[BUILDING.md](BUILDING.md).

---

## 1. Versioning

* **Semantic versioning** `MAJOR.MINOR.PATCH`, single source of truth:
  the `version` field in the root `package.json`.
* Tags are `vX.Y.Z` (e.g. `v1.0.0`); `release.yml` fails if the tag does not
  match `package.json`.
* Product releases follow user-facing meaning: `MINOR` for new features,
  `PATCH` for fixes, `MAJOR` only for breaking data/backup compatibility.

### Version bump checklist

Bump these **together** in one commit before tagging:

| File | Field | Notes |
| --- | --- | --- |
| `package.json` | `version` | source of truth, e.g. `1.1.0` |
| `apps/mobile/android/app/build.gradle` | `versionCode` + `versionName` | `versionCode` is an integer that must strictly increase for Play Store; `versionName` = semver |
| `apps/mobile/ios/App/App.xcodeproj/project.pbxproj` | `MARKETING_VERSION` + `CURRENT_PROJECT_VERSION` | in both Debug and Release configurations |
| `flatpak/org.deurge.DeUrge.metainfo.xml` | `<release version= date=>` | newest release first; AppStream requires it |
| `apps/desktop/package.json`, `apps/mobile/package.json`, `packages/core/package.json` | `version` | keep in step with the root version |

Then:

```bash
pnpm install --frozen-lockfile   # lockfile must be unchanged; commit it if deps changed
pnpm typecheck && pnpm test && pnpm --filter @deurge/web build && pnpm audit:privacy
```

Finally update the changelog/release notes draft and commit everything before
tagging (CI builds from the tag).

## 2. Artifact names

All artifacts are attached to the GitHub release and covered by
`SHA256SUMS.txt` (generated by the publish job and per-platform CI).

| Platform | Artifact | Built by |
| --- | --- | --- |
| Web/PWA | `deUrge-<version>-web.zip` | `web` job (`apps/web/dist`) |
| Android | `deUrge-<version>-debug.apk` (CI fallback) / `deUrge-<version>-release.apk` / `deUrge-<version>-release.aab` | `android` job |
| Linux AppImage | `deUrge-<version>-<arch>.AppImage` | `linux-appimage` job |
| Linux Flatpak | `deUrge-<version>-<arch>.flatpak` | `flatpak` job |
| Windows | `deUrge-Setup-<version>-<arch>.exe` | `windows` job |
| macOS | `deUrge-<version>-<arch>.dmg` | `macos` job |
| iOS (unsigned) | `deUrge-<version>-unsigned.xcarchive.zip` | `ios` job |
| Checksums | `SHA256SUMS.txt` | publish job (all files) |

`<arch>` is `x86_64`/`aarch64` for Linux, `x64`/`arm64` for Windows/macOS,
matching electron-builder/`uname -m` output.

## 3. Signing and secrets (never in the repo)

### Android (APK/AAB)

The release keystore is generated once, stored in a password manager, and
provided to CI as secrets:

| Secret | Value |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | `base64 -w0 "$HOME/deurge-release.jks"` |
| `ANDROID_KEYSTORE_PASSWORD` | store password |
| `ANDROID_KEY_ALIAS` | key alias (e.g. `deurge`) |
| `ANDROID_KEY_PASSWORD` | key password |

The workflow writes them to `$RUNNER_TEMP/deurge-release.jks`, exports the
`DEURGE_*` variables, builds, and deletes the keystore afterwards. Locally the
same variables are read by `apps/mobile/android/app/build.gradle`; without them
the release variant falls back to **debug signing** (useful for testing, not
for distribution).

Keystore creation (one-time, outside the repo):

```bash
keytool -genkeypair -v -keystore "$HOME/deurge-release.jks" -alias deurge \
  -keyalg RSA -keysize 4096 -validity 10000 -storetype PKCS12
```

Play Console upload uses the `.aab`; `versionCode` must increase monotonically.
Never delete or rotate the upload keystore without using Play App Signing key
rotation — losing it means losing update rights.

### Windows (NSIS installer)

electron-builder reads standard variables, so provide them as CI secrets and it
signs automatically:

| Secret | Notes |
| --- | --- |
| `CSC_LINK` | base64 of a `.pfx` (or a URL) |
| `CSC_KEY_PASSWORD` | certificate password |

Unsigned installers are fine for testing; SmartScreen will warn end users.

### macOS (DMG)

Unsigned DMGs work locally but Gatekeeper blocks them on other Macs. For real
distribution provide:

| Secret | Notes |
| --- | --- |
| `CSC_LINK` | Developer ID Application certificate (base64 `.p12`) |
| `CSC_KEY_PASSWORD` | certificate password |
| `APPLE_ID` | Apple ID for notarization |
| `APPLE_APP_SPECIFIC_PASSWORD` | app-specific password |
| `APPLE_TEAM_ID` | 10-character team id |

`apps/desktop/electron-builder.yml` has `hardenedRuntime: true` and the
entitlements in `apps/desktop/build/entitlements.mac.plist`; notarization is
performed by electron-builder when the Apple variables are present. Without
them the DMG is unsigned (`CSC_IDENTITY_AUTO_DISCOVERY=false` in CI).

### iOS

Store builds require an Apple Developer account. The CI workflow produces an
**unsigned** `.xcarchive`; a maintainer (or a signing job with
`DEVELOPMENT_TEAM`, a distribution certificate and a provisioning profile)
signs and exports it, then uploads to App Store Connect with Transporter/Xcode.

### Flatpak / Flathub

The `.flatpak` bundle is unsigned: users install it with
`flatpak install --user --bundle …` (or a maintainer submits the manifest to
Flathub). No Flathub token is required for the GitHub release artifact. If you
mirror a Flatpak repository, use a GPG key stored only in CI secrets.

## 4. Release procedure

1. **Freeze and verify** `main`:
   ```bash
   pnpm install --frozen-lockfile
   pnpm typecheck && pnpm test
   pnpm --filter @deurge/web build && pnpm audit:privacy
   ```
2. **Bump versions** (table above) and commit:
   `chore(release): vX.Y.Z`.
3. **Tag and push**:
   ```bash
   git tag -a vX.Y.Z -m "deUrge vX.Y.Z"
   git push origin main --tags
   ```
4. **Watch the `Release` workflow** (Actions → Release). It runs eight build
   jobs in parallel (web, android, linux AppImage, flatpak, windows, macos,
   ios), flattens all artifacts, writes `SHA256SUMS.txt` and creates a **draft**
   GitHub release named `deUrge vX.Y.Z` with generated notes.
5. **Verify the draft**:
   * every expected artifact from §2 is attached (a missing `ios`/`macos`
     artifact means a runner failure — inspect logs before publishing);
   * `SHA256SUMS.txt` is attached and matches the files;
   * release notes look right (edit them in the GitHub UI).
6. **Publish** the draft when the artifacts are verified.
7. **Store uploads** (manual, per store):
   * Google Play Console ← `…-release.aab` (internal → alpha → production);
   * App Store Connect ← signed iOS archive;
   * Microsoft Store / direct download ← signed `.exe`;
   * macOS: notarized `.dmg` (direct download);
   * Flathub: submit/update `flatpak/org.deurge.DeUrge.yml` on Flathub;
   * web: Netlify builds `main` automatically (`netlify.toml`), or upload
     `deUrge-<version>-web.zip` to any static host.

### Local release build (no CI)

```bash
pnpm install --frozen-lockfile
pnpm --filter @deurge/web build
pnpm build:desktop                     # Linux unpacked
pnpm --filter @deurge/desktop dist:linux
pnpm build:android                     # debug unless DEURGE_* signing vars set
pnpm build:flatpak                     # needs flatpak-builder/docker
```

Artifacts land in `apps/desktop/release/`, `apps/mobile/dist/`,
`flatpak/dist/`. Compute checksums with `sha256sum` (Linux) or `shasum -a 256`
(macOS) before uploading.

## 5. Verifying a release (for users and maintainers)

```bash
# download the artifact + SHA256SUMS.txt from the GitHub release, then:
sha256sum -c SHA256SUMS.txt          # Linux
shasum -a 256 -c SHA256SUMS.txt      # macOS
```

Platform checks:

* **Web**: host the zip contents statically; the app must work with the network
  disabled after first load (service worker).
* **Android**: `apksigner verify --print-certs <apk>` (CI does this), then
  `adb install -r` on a device.
* **AppImage**: `chmod +x deUrge-*.AppImage && ./deUrge-*.AppImage`.
* **Flatpak**: `flatpak install --user --bundle deUrge-*.flatpak` then
  `flatpak run org.deurge.DeUrge`; verify the sandbox has no network access and
  the database lives under `~/.var/app/org.deurge.DeUrge/`.
* **Electron desktop**: first launch creates `deurge.db` in the OS user-data
  directory; the window must load `app://deurge/index.html` and never make a
  network request.

## 6. CI/CD reference

| Workflow | Release responsibility |
| --- | --- |
| `.github/workflows/release.yml` | tag `v*` → all platform artifacts + `SHA256SUMS.txt` + draft GitHub release |
| `.github/workflows/ci.yml` | PR/main gate: typecheck, tests, web build, privacy audit, Electron packaging smoke |
| `.github/workflows/android.yml` | per-push APK (debug) / tag APK+AAB (signed when secrets exist) |
| `.github/workflows/flatpak.yml` | `.flatpak` bundle |
| `.github/workflows/desktop-{linux,windows,macos}.yml` | AppImage / NSIS / DMG |
| `.github/workflows/ios.yml` | unsigned simulator build + unsigned `.xcarchive` |

Actions caches: pnpm store (`setup-node cache: pnpm`), Electron/electron-builder
downloads (`~/.cache/electron*`, `~/Library/Caches/electron*`,
`~/AppData/Local/electron*`), Gradle (`gradle/actions/setup-gradle`).

## 7. Rollback / yanking

* **GitHub release**: unpublish or mark the draft/unpublished release; delete
  the tag only if the build was never consumed (`git tag -d vX.Y.Z` +
  `git push origin :refs/tags/vX.Y.Z`) and ship `vX.Y.(Z+1)` instead.
* **Play Store**: roll out a new `versionCode`; you cannot decrease it. Use
  staged rollout halt + hotfix.
* **App Store**: remove from sale or expedite a new build; builds are immutable.
* **Web**: redeploy the previous `deUrge-<version>-web.zip` (service workers
  update on next load; keep the previous release zip).
* **Flatpak/AppImage/desktop**: publish patched artifacts with the next patch
  version; never replace an already-published file with different bytes.
* Keep `SHA256SUMS.txt` attached to old releases so users can verify what they
  downloaded.


## Published releases

Publishing is idempotent: re-running this workflow uploads rebuilt artifacts to an existing *draft* release, and leaves an already-published release's assets untouched (the rebuilt files remain available as workflow artifacts). A maintainer can therefore publish locally built, signed artifacts first (as done for `v1.0.0`) and still validate the pipeline.
